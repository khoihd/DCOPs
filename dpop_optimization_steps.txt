DPOP optimization plan
======================

Goal
----
Optimize `pydcop/algorithms/dpop.py` conservatively, preserving DPOP message
semantics and optimality.

Current code map
----------------
- `computation_memory()` estimates the UTIL relation footprint from the
  computation variable and separator.
- `DpopMessage.size` estimates UTIL and VALUE message sizes.
- `DpopAlgo.__init__()` filters constraints so each relation is managed by the
  lowest DFS-tree computation.
- `_compute_utils_msg()` joins local constraints into accumulated child UTILs,
  then projects out the computation variable.
- `_on_util_message()` accumulates child UTILs and triggers UTIL or VALUE phase.
- `_on_value_message()` slices the joined UTIL relation with separator values,
  selects the local value, and forwards VALUE messages to children.

Priority 2: constructor constraint filtering
--------------------------------------------
[x] Step 2 complete

Why:
- `DpopAlgo.__init__()` copies constraints, then removes constraints while
  scanning descendant names.
- It rebuilds each relation's scope-name list and uses list membership.
- This is startup overhead, but it is low risk and easy to test.

Expected impact:
- Runtime: small constant-factor improvement during computation construction.
- Space: unchanged.

Implementation:
[x] Replace remove-from-copy logic with append-to-filtered-list logic.
[x] Use a descendant-name set.
[x] Ignore using each relation's `scope_names` or a local tuple of variable
    names once. The current local set comprehension avoids a broader
    relation-protocol change and is already scoped to this filter.
[x] Preserve exactly which constraints are kept or filtered.

Tests:
[x] Add focused tests for constraints kept when they only involve self,
    parent, or pseudo-parents.
[x] Add focused tests for constraints filtered when they involve children or
    pseudo-children.

[x] conda run -n khoihd ruff check pydcop/algorithms/dpop.py tests/unit/test_algorithms_dpop.py


Priority 3: VALUE message intersection cleanup
----------------------------------------------
[x] Step 3 complete

Why:
- `_on_value_message()` builds child VALUE messages by trying to read every
  child separator variable from `value_dict` and ignoring `KeyError`.
- This is small, but replacing exception-driven control flow with membership
  checks is clearer and cheaper.

Expected impact:
- Runtime: small constant-factor improvement in VALUE propagation.
- Behavior: unchanged child VALUE contents and order.

Implementation:
[x] Replace `try` / `except KeyError` with `if v.name in value_dict`.
[x] Preserve child separator order in outgoing VALUE messages.

Tests:
[x] Add or confirm a test where a child separator contains variables both in
    and outside the received separator.

Priority 4: relation join/projection phase review
-------------------------------------------------
[ ] Step 4 complete

Why:
- `_compute_utils_msg()` is the main DPOP hot path: it joins child UTILs and
  local constraints, then projects out the local variable.
- Changing join order or pre-converting constraints can change intermediate
  dimensions and tie behavior, so this needs profiling and oracle checks first.

Possible changes:
[ ] Measure whether local function constraints should be converted to
    `NAryMatrixRelation` before joining.
[ ] Measure whether ordering local joins by relation size/arity reduces
    intermediate matrix sizes.
[ ] Consider a helper that joins local constraints exactly once, but only if it
    improves clarity without changing message timing assumptions.

Risks:
- Join dimension order is visible in UTIL relations.
- Tie-breaking can depend on relation dimension and value order.
- Memory can get worse if a size-based order expands dimensions earlier.
