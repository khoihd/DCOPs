Relation optimization actionable steps
======================================

Goal
----
Optimize remaining hot relation operations in pydcop/dcop/relations.py without
changing public behavior.

-----------------------------------------
[x] Step 1 complete

Why:
- DPOP calls projection() when computing UTIL messages.
- projection() previously filled a result relation through repeated
  set_value_for_assignment() calls, which copies the full matrix each time.
- projection() now dispatches to projection_fast() for NAryMatrixRelation and
  projection_slow() for generic relation implementations.

Implementation:
[x] Keep the existing generic projection() behavior as fallback.
[x] Add a fast path for isinstance(a_rel, NAryMatrixRelation).
[x] Move the matrix path into projection_fast().
[x] Move the generic path into projection_slow().
[x] Find the projected axis with a_rel.dimensions.index(a_var).
[x] Build remaining_vars exactly as today.
[x] Use np.max(a_rel._m, axis=axis) for mode == "max".
[x] Use np.min(a_rel._m, axis=axis) for mode == "min".
[x] Return NAryMatrixRelation(remaining_vars, matrix).
[x] Preserve existing error behavior for invalid mode where practical.
[x] Avoid repeated result-matrix copies in projection_slow().

Priority 2: projection_slow() direct generic evaluation
-------------------------------------------------------
[x] Step 2 complete

Why:
- projection_slow() is now the generic fallback used by projection() for
  non-NAryMatrixRelation relations.
- projection_slow() already avoids repeated result-matrix copies.
- It still creates one sliced relation per partial assignment and then calls
  find_arg_optimal() on that slice.
- Avoiding the slice object creation could reduce overhead for function-backed
  relations while keeping projection() behavior unchanged.

Risk:
- This is more behavior-sensitive than the matrix fast path because
  projection_slow() handles all non-matrix relation implementations.
- Preserve current mode validation and relation error behavior where practical.
- Keep the current slice() + find_arg_optimal() path available as a fallback if
  direct relation evaluation is not safe for a relation type.

Implementation:
[x] Keep projection() as the main dispatcher.
[x] Keep projection_fast() unchanged.
[x] In projection_slow(), keep remaining_vars exactly as today.
[x] Pre-validate mode or preserve find_arg_optimal() invalid-mode behavior.
[x] For each partial assignment, evaluate candidate assignments directly when
    practical: set a_var.name to each domain value and call the relation with
    get_value_for_assignment().
[x] Track the best projected value without creating a sliced relation.
[x] Write the best value directly into the raw result matrix.
[x] Fall back to the current slice() + find_arg_optimal() behavior if direct
    evaluation would change compatibility.

Tests:

[x] Add or confirm projection_slow() tests for min and max modes.
[x] Add or confirm projection_slow() tests for one-variable/scalar projection.
[x] Add or confirm projection_slow() result parity with projection_fast() on a
    matrix relation used directly in tests.
[x] Add or update benchmark-style coverage for projection_slow().

Priority 5: NAryMatrixRelation._slice_matrix()
----------------------------------------------
[ ] Step 5 complete

Why:
- NAryMatrixRelation.slice() is used outside DPOP by MGM, DBA, Mixed DSA, and
  Dynamic Max-Sum, so matrix-slice overhead can affect several algorithms.
- _slice_matrix() currently rebuilds variable-name lists on every call.
- It uses repeated list membership checks and s_vars.index(...) lookups.
- It calls v.domain.index(val), which is linear in the variable domain size.

Risk:
- slice() has broad algorithm usage, so preserve current behavior carefully.
- Keep ignore_extra_vars behavior compatible, including error behavior for
  unknown variables when ignore_extra_vars is False.
- Avoid adding persistent caches unless profiling shows the per-call dict
  optimization is not enough.

Implementation:
[ ] Keep NAryMatrixRelation.slice() public behavior unchanged.
[ ] Replace repeated s_vars membership/index lookups with a per-call assignment
    dict built from sliced_vars and sliced_values.
[ ] Preserve the returned slice_vars order.
[ ] Preserve the returned tuple containing scalar indexes and slice(None).
[ ] Consider per-call domain value index maps only if tests/profiling justify it.
[ ] Do not introduce relation-level caches in this step.

Tests:
[ ] Run existing NAryMatrixRelationSliceTest.
[ ] Add or confirm tests for unknown sliced variables with ignore_extra_vars
    False.
[ ] Add or confirm tests for ignore_extra_vars True.
[ ] Add or confirm tests for slicing first, middle, and last matrix axes.
[ ] Add benchmark-style coverage only if the change is measurable and stable.
