Relation optimization plan
==========================

Goal
----
Continue optimizing hot relation operations in pydcop/dcop/relations.py
without changing public behavior.


Completed work
--------------
[x] projection() matrix fast path:
    - projection() dispatches NAryMatrixRelation to projection_fast().
    - projection_fast() uses np.max/np.min over the projected axis.
    - projection_slow() remains the generic fallback.

[x] projection_slow() direct generic evaluation:
    - Avoids creating a sliced relation for each partial assignment when
      direct get_value_for_assignment() evaluation works.
    - Falls back to slice() + find_arg_optimal() for relation types that
      cannot be evaluated directly.
    - Iterates projected matrix coordinates directly with np.ndindex().

[x] NAryMatrixRelation.from_func_relation():
    - Allocates one raw matrix and fills it directly.
    - Avoids repeated set_value_for_assignment() calls and full matrix copies.

[x] NAryMatrixRelation.get_value_for_assignment():
    - Computes matrix indexes directly for list and dict assignments.
    - Avoids creating temporary sliced relations for scalar lookup.


Review notes
------------
- DPOP projection/join on matrix-backed relations is now the best-optimized
  path in this file.
- The remaining matrix hot path is explicit slicing:
  NAryMatrixRelation.slice() -> _slice_matrix().
- _slice_matrix() bookkeeping is now optimized, reducing explicit slice overhead.
- Generic join() still uses generate_assignment_as_dict(), filter_assignment_dict(),
  and domain.index() inside the fallback loop; it is the next best target.
- set_value_for_assignment() still copies the whole matrix by design, so its
  remaining improvement is mostly constant-factor index setup.
- assignment_cost(), find_optimal(), and filter_assignment_dict() are used by
  several local-search algorithms; optimize them only with targeted tests.

Notation used below:
- n: relation arity or number of variables in a relation.
- k: number of variables in a partial assignment.
- d: typical variable domain size.
- M: number of cells in the relevant output/full matrix.


Priority 1: NAryMatrixRelation._slice_matrix()
----------------------------------------------
[x] Step 1 complete

Why:
- slice() is still used by MGM, DBA, Mixed DSA, Dynamic Max-Sum, DPOP value
  selection, ConditionalRelation, and tests.
- _slice_matrix() rebuilds variable-name lists on every call.
- It uses repeated list membership checks and s_vars.index(...) lookups.
- It calls v.domain.index(val), which is linear in the variable domain size.

Expected complexity impact:
- Runtime: reduce per-call bookkeeping from roughly O(k*n + n*k + k*d) to
  O(n + k + k*d). The output slice itself is unchanged.
- Space: same O(n + k) temporary scale, with fewer intermediate parallel lists
  and scans.
- Note: domain.index(val) remains O(d) in this step; remove only if profiling
  shows it is still material.

Risk:
- slice() has broad algorithm usage.
- Preserve ignore_extra_vars behavior exactly, including unknown-variable
  errors when ignore_extra_vars is False.
- Avoid persistent caches in this step; keep it local and easy to review.

Implementation:
[x] Replace s_vars/s_values parallel lists with a per-call assignment dict.
[x] Use a per-call set of relation variable names for unknown-variable checks.
[x] Preserve the returned slice_vars order.
[x] Preserve the returned tuple of scalar indexes and slice(None).
[x] Keep domain.index(val) for now unless profiling shows it is still a
    meaningful cost after removing list scans.

Tests:

[x] Add or confirm tests for unknown sliced variables with ignore_extra_vars
    False.
[x] Add or confirm tests for ignore_extra_vars True.
[x] Add or confirm tests for slicing first, middle, and last matrix axes.

Priority 2: generic join() fallback
-----------------------------------
[x] Step 2 complete

Why:
- Matrix + matrix join is optimized, but non-matrix joins still use the generic
  fallback.
- The fallback loop currently uses generate_assignment_as_dict(dims),
  filter_assignment_dict() twice, and domain.index() to recover matrix
  coordinates.
- Function-backed constraints can still reach this path before conversion to
  matrix relations.

Expected complexity impact:
- Runtime: the unavoidable O(M) output-cell loop remains, but per-cell overhead
  drops by avoiding recursive assignment generation, repeated filtering setup,
  and domain.index() coordinate recovery.
- Current shape: roughly O(M * (n*d + filter overhead + relation evals)).
- Planned shape: roughly O(M * (n + arity(u1) + arity(u2) + relation evals)).
- Space: output matrix remains O(M); per-cell temporary assignments should be
  similar or smaller, with no recursive generator stack.

Risk:
- Join dimension ordering is user-visible through the returned relation.
- Generic relations may differ in whether they prefer kwargs, dict positional
  calls, or get_value_for_assignment().

Implementation:
[x] Split join() into dispatcher, join_fast(), and join_slow().
[x] Keep the existing matrix + matrix fast path unchanged in join_fast().
[x] In the fallback, allocate the result matrix once as today.
[x] Iterate result matrix coordinates with np.ndindex(matrix.shape).
[x] Build one full assignment dict from coordinates.
[x] Build u1/u2 assignment dicts with precomputed relation variable-name tuples.
[x] Evaluate u1 and u2 exactly as today, or add a conservative direct-eval
    helper with fallback if needed.
[x] Write directly to matrix[matrix_index].

Tests:

[x] Add a regression test that join_slow() does not use assignment generation
    or filtering helpers.
[x] Run existing join tests.
[x] Add or confirm tests for matrix/function joins.
[x] Add or confirm tests for different variable order.
[x] Add or confirm tests for zero-arity joins.
[x] Add benchmark-style coverage comparing join_fast() and join_slow().

Priority 3: NAryMatrixRelation.set_value_for_assignment()
---------------------------------------------------------
[x] Step 3 complete

Why:
- Before this step, set_value_for_assignment() reused the optimized
  _slice_matrix() bookkeeping in both list and dict branches.
- This step stops routing full scalar assignments through _slice_matrix() and
  computes the full index tuple directly.
- It still copies the full matrix on each call because the public API returns a
  new relation instead of mutating self.
- Generators for graph coloring, meetings, IoT/Ising-style instances use this
  method repeatedly while building constraints.

Expected complexity impact:
- Runtime: keep the unavoidable O(M) full matrix copy, but reduce remaining
  scalar index setup to a simple O(n + n*d) pass for full assignments.
- Space: unchanged O(M), because the API returns a new relation and must copy
  the matrix.
- Note: this improves constants; it does not change the main asymptotic cost
  while copy-on-write behavior is preserved.

Risk:
- Public immutability behavior must remain unchanged.
- Error behavior for list, dict, missing variable, and invalid values should
  stay compatible.

Implementation:
[x] Previous baseline reused the optimized _slice_matrix() bookkeeping.
[x] Replace _slice_matrix() calls with direct scalar index tuple construction.
[x] For list input, compute the full scalar index tuple directly from variable
    order.
[x] For dict input, compute the full scalar index tuple directly from variable
    names.
[x] Keep exactly one np.copy(self._m) per call.
[x] Return NAryMatrixRelation(self._variables, matrix, name=self.name).

Tests:
[x] Run existing set_value_for_assignment tests.

Priority 4: assignment generation helpers
-----------------------------------------
[x] Step 4 complete

Why:
- generate_assignment() and generate_assignment_as_dict() are recursive.
- They are used by YAML dumping, oracle tests, local-search algorithms, and
  generic relation helpers.
- Some hot paths no longer use them after the projection and conversion work,
  so this should be done only after checking remaining call sites.

Expected complexity impact:
- Runtime: still O(M*n) to emit M assignments of size n, but with lower
  constant overhead by replacing recursion with itertools.product.
- Space: should remain streaming O(n) per yielded assignment, with no O(M)
  materialization. Recursion stack can drop from O(n) to iterator-local state.
- Note: iteration order and yielded object mutability are more important than
  asymptotic complexity here.

Risk:
- Existing generators mutate and yield assignment objects in a specific order.
- Changing iteration order can affect tests and reproducibility.
- Some callers may rely accidentally on yielded dict mutability.

Implementation:
[x] First document current iteration order with focused tests.
[x] Consider replacing recursion with itertools.product over domains.
[x] Preserve yielded list/dict shape and variable order.
[x] Avoid changing callers in the same patch unless needed.

Tests:

Priority 5: assignment_cost(), find_optimal(), and filter_assignment_dict()
--------------------------------------------------------------------------
[ ] Step 5 deferred

Why:
- assignment_cost() and find_optimal() are used in DSA, ADSA, MGM2, SyncBB,
  NCBB, and tests.
- filter_assignment_dict() is simple but called in many loops.
- These helpers are algorithm-facing and can affect runtime broadly.

Decision:
- Leave assignment_cost() unchanged for now. It is already manually tuned,
  shared broadly by algorithms, and any likely gain is a constant-factor
  improvement with higher behavior risk than the previous relation helper
  optimizations.
- Revisit only if profiling shows assignment_cost() or repeated assignment
  filtering is a clear hotspot.

Expected complexity impact:
- Runtime: likely constant-factor improvement rather than a new asymptotic
  class. Repeated filtering can move from rebuilding target-name lists each
  call to reusing precomputed names.
- find_optimal() remains O(|domain(variable)| * assignment_cost).
- assignment_cost() remains O(sum constraint arities) per evaluated assignment.
- Space: should remain O(max constraint arity) per cost evaluation.

Risk:
- This area is behavior-sensitive because many algorithms share it.
- Missing-value fallback through **kwargs in assignment_cost() must remain
  compatible.
- Variable cost handling must remain compatible.

Implementation:
[ ] Profile or write a small benchmark before changing this step.
[ ] Precompute target variable names where a caller repeatedly filters for the
    same relation dimensions.
[ ] Consider a private helper for filtering by a precomputed name tuple/set.
[ ] Keep public filter_assignment_dict() behavior unchanged.
[ ] Do not combine this with algorithm rewrites.

Tests:
[ ] Run assignment_cost and find_optimal tests.
[ ] Run DSA/ADSA/MGM2 focused tests when touching these helpers.

Priority 6: low-priority cleanup candidates
-------------------------------------------
[ ] Step 6 complete

Candidates:
- ConditionalRelation.dimensions recomputes and sorts dimensions on each access.
- NAryFunctionRelation.slice() rebuilds variable-name lists on each call.
- find_optimum() still filters generated full assignments before evaluation.
- NAryMatrixRelation.__hash__ hashes str(self._m), which is fast-ish but
  imprecise and can still be expensive for large matrices.

Expected complexity impact:
- ConditionalRelation.dimensions caching could turn repeated dimension access
  from O(n log n) sorting per call into O(1) after construction, at the cost of
  storing a cached list.
- NAryFunctionRelation.slice() cleanup would mostly reduce O(n*k) list scans to
  O(n + k), similar to the matrix slice step.
- find_optimum() improvements would keep the O(M) exhaustive search but reduce
  assignment filtering overhead per cell.
- NAryMatrixRelation.__hash__ changes are riskier; any improvement must
  preserve hash/equality expectations.

Guidance:
[ ] Do not optimize these without a failing benchmark, profile, or algorithm
    need.
[ ] Keep behavior-preserving cleanup separate from performance patches.
[ ] Prefer narrow tests over broad refactors.
