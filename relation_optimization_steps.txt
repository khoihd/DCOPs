Relation optimization actionable steps
======================================

Goal
----
Optimize remaining hot relation operations in pydcop/dcop/relations.py without
changing public behavior.


Priority 1: projection() matrix fast path
-----------------------------------------
[ ] Step 1 complete

Why:
- DPOP calls projection() when computing UTIL messages.
- projection() currently fills a result relation through repeated
  set_value_for_assignment() calls, which copies the full matrix each time.

Implementation:
[ ] Keep the existing generic projection() behavior as fallback.
[ ] Add a fast path for isinstance(a_rel, NAryMatrixRelation).
[ ] Find the projected axis with a_rel.dimensions.index(a_var).
[ ] Build remaining_vars exactly as today.
[ ] Use np.max(a_rel._m, axis=axis) for mode == "max".
[ ] Use np.min(a_rel._m, axis=axis) for mode == "min".
[ ] Return NAryMatrixRelation(remaining_vars, matrix).
[ ] Preserve existing error behavior for invalid mode where practical.

Tests:
[ ] Add or confirm projection tests for projecting the first axis.
[ ] Add or confirm projection tests for projecting a middle axis.
[ ] Add or confirm projection tests for projecting the last axis.
[ ] Add or confirm min and max modes.

Priority 2: NAryMatrixRelation.from_func_relation()
---------------------------------------------------
[ ] Step 2 complete

Why:
- from_func_relation() currently creates an empty NAryMatrixRelation and fills
  it through repeated set_value_for_assignment() calls.
- This is less central to DPOP than projection(), but it has the same repeated
  full-matrix copy pattern.

Implementation:
[ ] Allocate one raw NumPy matrix with shape tuple(len(v.domain) for v in variables).
[ ] Iterate over generate_assignment_as_dict(variables).
[ ] Evaluate the source relation exactly as today.
[ ] Write the value directly into the raw matrix.
[ ] Return one NAryMatrixRelation(variables, matrix, name=rel.name).

Tests:
[ ] Run existing NAryMatrixRelationFromFunctionTests.
[ ] Add a test only if existing coverage misses a behavior changed by the patch.

Priority 3: scalar lookup in NAryMatrixRelation.get_value_for_assignment()
-------------------------------------------------------------------------
[ ] Step 3 complete

Why:
- get_value_for_assignment() currently calls slice() and constructs a temporary
  NAryMatrixRelation just to return one scalar.
- Direct matrix indexing would reduce overhead in generic relation code paths.

Risk:
- This is more behavior-sensitive than Priority 1 and 2 because scalar lookup,
  list assignment lookup, dict assignment lookup, zero-arity lookup, and error
  handling all need to remain compatible.

Implementation:
[ ] Keep zero-arity behavior unchanged.
[ ] For list input, compute the index tuple directly from variable order.
[ ] For dict input, compute the index tuple directly from variable names.
[ ] Return self._m[index_tuple].item().
[ ] Preserve current ValueError/KeyError behavior where practical.

Tests:
[ ] Run existing NAryMatrixRelation value lookup tests.
[ ] Add tests for dict lookup with variables in different order if needed.
[ ] Add tests for missing assignment values if behavior is unclear.
